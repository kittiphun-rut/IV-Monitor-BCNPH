# รายงานตรวจความพร้อมก่อนผลิตจริง — Smart IV Alert

เอกสารนี้เป็นผลการตรวจโค้ดทั้งรีโพ เพื่อตอบคำถามว่า **ต้องแก้อะไรบ้าง
ระบบนี้จึงจะเอาไปใช้กับผู้ป่วยจริงได้อย่างปลอดภัย** ทุกข้อมีหลักฐานอ้างอิง
เป็นชื่อไฟล์และเลขบรรทัด ไม่ใช่ความเห็นลอย ๆ

ตรวจ ณ commit `fb00fd7` ครอบคลุมเฟิร์มแวร์ ๗ สาย รวม ๒๑,๖๖๙ บรรทัด

## 🔴 ข้อที่ขวางการใช้งานจริง

### ๑. เตียงหลุดการติดต่อขณะกำลังให้น้ำเกลือ แล้ว Host เงียบสนิท

**หลักฐาน** `firmware/Host-OLED/Host-OLED.ino:924-930`

```cpp
if (!isStationOnline(i) || !s.isRunning) {
  if (s.alertCode != ALERT_NONE) requestSyncNow(i);
  s.alertCode = ALERT_NONE;      // <-- ล้างเหตุเตือนทิ้ง
  s.deviationSince = 0;
  continue;                      // <-- ข้ามไปเตียงถัดไป ไม่มีเสียงใด ๆ
}
```

พบรูปแบบเดียวกันที่ `Host-TFT28.ino:576` และ `Host-Touch24.ino:984`

**เกิดอะไรขึ้นจริง** เครื่องที่เตียงแบตหมด สายหลุด บอร์ดค้าง หรือถูกถอดปลั๊ก
ระหว่างที่ผู้ป่วยยังรับน้ำเกลืออยู่ → ที่ Host จอจะขึ้นคำว่า `OFFLINE` เท่านั้น
**ไม่มีเสียง ไม่มีการยกระดับ** พยาบาลที่อยู่อีกห้องหนึ่งจะไม่รู้เลยว่า
เตียงนั้นเลิกถูกเฝ้าไปแล้ว

**ทำไมถึงร้ายแรงกว่าที่เห็น** นี่คือความล้มเหลวแบบเงียบชนิดเดียวกับที่
ผู้พัฒนาเคยระบุไว้เองในหัวไฟล์ `Host-OLED.ino:97-101` ตอนเพิ่ม `ALERT_NO_SIGNAL`
ว่า *"นี่คือความล้มเหลวแบบเงียบ ซึ่งอันตรายกว่าการแจ้งเตือนผิด เพราะพยาบาล
เข้าใจว่าระบบกำลังเฝ้าอยู่ ทั้งที่ไม่ได้นับอะไรเลย"* — เหตุผลนั้นถูกต้องทุกคำ
และใช้ได้กับกรณีเตียงหลุดเหมือนกันทุกประการ แต่กรณีนี้ยังไม่ถูกแก้

**ทางแก้ที่เสนอ** เพิ่มรหัส `ALERT_LOST_LINK` ที่ใช้ **เฉพาะฝั่ง Host**
เงื่อนไข: เตียงนั้นเคยออนไลน์ + กำลังนับอยู่ + เงียบไปเกินระยะผ่อนผัน
ไม่ต้องแตะโครงสร้างแพ็กเก็ต เพราะรหัสนี้ไม่เคยถูกส่งออกไปที่ Station
ใช้วิธีเดียวกับที่ `syncAlertFor()` แปลง `ALERT_NO_SIGNAL` เป็น `ALERT_NONE` อยู่แล้ว
(`Host-OLED.ino:425-428`) จึงเข้ากันได้ย้อนหลังกับ Station ทุกรุ่น

### ๒. ปริมาตรที่ให้ไปแล้วหายหมดเมื่อไฟดับหรือบอร์ดรีบูต

**หลักฐาน** `firmware/Station/Station.ino:347,352`

```cpp
uint32_t totalDrops   = 0;    // อยู่ใน RAM อย่างเดียว
float    totalVolumeMl = 0.0;
```

ค่าที่เขียนลง NVS มีแต่ค่าปรับเทียบเซนเซอร์ (`st_cal`) และค่าตั้งเครื่อง
(`st_cfg`: เลขเตียง ช่องสัญญาณ การหมุนจอ) — ดูรายการทั้งหมดที่บรรทัด
`793-805, 1015-1017, 1318-1320, 1498-1502, 1628-1630` **ไม่มีการเก็บตัวนับหยดเลย**

ฝั่ง Host ก็กู้ให้ไม่ได้ เพราะ Host คัดลอกค่าจาก Station ตรง ๆ
(`Host-OLED.ino` ในคอลแบ็ก: `s.totalDrops = incoming.totalDrops;`)
และยังมีโค้ดที่ตีความว่าค่าลดลง = Station รีบูต แล้วยอมรับค่าใหม่ทันที

**เกิดอะไรขึ้นจริง** ไฟตกในวอร์ดสักครึ่งวินาที หรือบอร์ดรีเซ็ตเอง
→ ตัวเลข "ให้ไปแล้วกี่ mL" กลับเป็นศูนย์ → แผนการให้ยาที่ตั้งไว้เพี้ยนทั้งถุง
→ การเตือน "ใกล้หมด" และ "ครบตามแผน" จะมาช้ากว่าความจริงเท่ากับปริมาตรที่หายไป

นี่คือข้อบกพร่องที่มีผลทางคลินิกตรงที่สุดในรีโพนี้

**ทางแก้ที่เสนอ** เก็บสองชั้น
* ชั้นเร็ว — `RTC_DATA_ATTR` เขียนทุกหยด ไม่กินอายุแฟลชเลย
  รอดจากการรีเซ็ตด้วยซอฟต์แวร์ วอตช์ด็อก และไฟตกชั่วขณะ
* ชั้นทน — เขียน NVS เป็นระยะ (เช่นทุก ๕ นาที และตอนกดหยุด) รอดไฟดับสนิท

ตอนบูต ถ้าลายเซ็นใน RTC ถูกต้องให้ใช้ค่านั้น ถ้าไม่ให้ถอยไปใช้ค่าใน NVS

### ๓. ไม่มีวอตช์ด็อก ไม่มีการรายงานสาเหตุการรีบูต

**หลักฐาน** ค้นทั้ง `firmware/` ด้วยคำว่า `esp_task_wdt` `watchdog` `esp_reset_reason`
`brownout` — **ไม่พบแม้แต่ที่เดียว**

**เกิดอะไรขึ้นจริง** ถ้า `loop()` ค้าง — บัส I2C ของจอค้าง สแต็ก Wi-Fi ค้าง
วนซ้ำในตัวจัดการคำขอเว็บ — เครื่องจะค้างคาอยู่อย่างนั้น จอค้างภาพเดิม
ไม่มีเสียงเตือน และ **ไม่มีอะไรมาปลุก** สำหรับเครื่องที่ทำหน้าที่เตือนภัย
การค้างแบบเงียบคือรูปแบบความล้มเหลวที่แย่ที่สุดเท่าที่จะเป็นได้

อีกด้านหนึ่ง เมื่อเครื่องรีบูตเอง ไม่มีใครรู้ว่าเพราะอะไร
ทำให้หาสาเหตุในวอร์ดจริงไม่ได้เลย

**ทางแก้ที่เสนอ** เปิด Task Watchdog ที่ ๘ วินาที ผูกกับงานที่รัน `loop()`
และเรียก `esp_task_wdt_reset()` ทุกรอบ พร้อมอ่าน `esp_reset_reason()` ตอนบูต
เก็บไว้แสดงในหน้าเว็บและใน API เพื่อให้ตามรอยได้

### ๔. รหัสผ่านฝังตายในโค้ด และถูกส่งกลับออกมาทางหน้าเว็บ

**หลักฐาน** `firmware/Host-OLED/Host-OLED.ino:237-239`

```cpp
const char *default_ap_pass = "12345678";
const char *web_username    = "admin";
const char *web_password    = "password123";
```

ค่าชุดเดียวกันอยู่ที่ `Host-TFT28.ino:148-150` และ `Host-Touch24.ino:214-215`
และรหัสผ่าน AP ยังถูกส่งกลับออกมาเป็น JSON ทาง HTTP ที่
`Host-OLED.ino:1640` และ `Host-TFT28.ino:1315`

```cpp
json += "\"password\":\"" + jsonEscape(default_ap_pass) + "\",";
```

**เกิดอะไรขึ้นจริง** ทุกเครื่องที่ผลิตออกมาจะมีรหัสผ่านเดียวกันหมด
และรหัสนั้นอยู่ในรีโพสาธารณะ ใครก็ตามที่อยู่ในรัศมีสัญญาณสามารถเข้าหน้าเว็บ
แก้อัตราการให้ยา เปลี่ยนแผนปริมาตร หรือกด "เริ่มถุงใหม่" เพื่อล้างตัวนับได้
ในโรงพยาบาลนี่ไม่ใช่แค่เรื่องความปลอดภัยสารสนเทศ แต่กระทบตัวผู้ป่วยโดยตรง

**ทางแก้ที่เสนอ** สร้างรหัสผ่านประจำเครื่องจาก MAC ตอนบูตครั้งแรก
เก็บใน NVS แสดงบนจอของเครื่องนั้นเอง (พยาบาลอ่านจากหน้าเครื่อง)
และ **เลิกส่งรหัสผ่านกลับออกมาทาง API** เด็ดขาด

## 🟠 ข้อที่ควรแก้ก่อนผลิต

### ๕. การนับเวลาพังเมื่อ `millis()` วนรอบ (๔๙.๗ วัน)

**หลักฐาน** `firmware/Station/Station.ino:1580` และ `Station-Stable.ino:2213`

```cpp
if (lr == 0 || (currentMillis > lr && currentMillis - lr > HOST_TIMEOUT_MS)) {
```

เงื่อนไข `currentMillis - lr > HOST_TIMEOUT_MS` เป็นวิธีที่ถูกต้องอยู่แล้ว
เพราะเลขไม่มีเครื่องหมายลบกันแล้ววนรอบได้เอง แต่การเติม `currentMillis > lr`
เข้าไปข้างหน้า **ทำลายคุณสมบัตินั้นทิ้ง** หลังตัวนับวนรอบ `currentMillis`
จะน้อยกว่า `lr` เงื่อนไขจึงเป็นเท็จตลอด → Station จะรายงานว่า
"Host ยังออนไลน์" ต่อไปอีกเกือบ ๕๐ วัน ทั้งที่ Host ดับไปแล้ว

รูปแบบเดียวกันอยู่ที่ `Host-TFT28.ino:1537` และ `Host-Touch24.ino:2548`
(`currentMillis > manualFocusUntil`) ซึ่งกระทบแค่การสลับหน้าจอ จึงเบากว่า

ที่เหลือทั้งรีโพใช้รูปแบบ `now - last >= period` ที่ปลอดภัยถูกต้องแล้ว
จึงเป็นข้อยกเว้นเฉพาะจุด ไม่ใช่ปัญหาเชิงระบบ

### ๖. แพ็กเก็ตไม่มีการตรวจความถูกต้องและปลอมได้

`struct_message` (`Host-OLED.ino:283-292`) มีแต่ข้อมูลล้วน ไม่มีเลขตรวจสอบ
ไม่มีลายเซ็น ไม่มีไบต์ระบุเวอร์ชันโปรโตคอล การตรวจมีเพียง
`if (len != sizeof(struct_message)) return;` และช่วงของ `stationId`

ผลคือ อุปกรณ์อื่นที่บังเอิญกระจาย ESP-NOW ขนาด ๒๓ ไบต์ในช่องเดียวกัน
จะถูกตีความเป็นข้อมูลเตียง และผู้ที่ตั้งใจก็ปลอมเลขเตียงได้ทันที

**ข้อจำกัด** โครงสร้างนี้ถูกตรึงไว้ให้เหมือนกันทุกไบต์ในทุกเฟิร์มแวร์
(`static_assert` ที่บรรทัด `308-309`) การเติมช่องใหม่จึงเท่ากับขึ้นโปรโตคอล v4
ซึ่งต้องแฟลชทุกเครื่องพร้อมกัน **จึงไม่ควรทำในรุ่นนี้**

**ที่ทำได้ทันทีโดยไม่แตะโครงสร้าง** คือปฏิเสธค่าที่เป็นไปไม่ได้ทางกายภาพ
(อัตราไหลติดลบ อัตราไหลสูงเกินจริง แรงดันแบตเตอรี่นอกช่วง `NaN`)
ช่วยกันทั้งแพ็กเก็ตขยะและข้อมูลเสียจากสัญญาณรบกวน

### ๗. บันทึกการให้ยาอยู่ใน RAM อย่างเดียว

`StationData::logs[MAX_LOGS]` (`Host-OLED.ino:382-383`) เป็นวงแหวนในหน่วยความจำ
ไฟดับครั้งเดียวบันทึกหายทั้งหมด สำหรับงานวิจัยที่ต้องใช้ข้อมูลย้อนหลัง
ควรมีทางเลือกเขียนลง LittleFS หรือการ์ด SD

### ๘. งานในคอลแบ็กรับข้อมูลทำเยอะและอยู่ในส่วนวิกฤต

คอลแบ็ก `OnDataRecv` ทำงานหลายสิบบรรทัดภายใน `portENTER_CRITICAL(&dataMux)`
ทั้งตรวจเลขเตียงซ้ำ เทียบ MAC คำนวณผลต่าง และคิดปริมาตร
คอลแบ็กนี้ถูกเรียกจากงานของ Wi-Fi การถือส่วนวิกฤตนานเกินไปมีโอกาสรบกวน
จังหวะของสแต็ก Wi-Fi เอง ควรย้ายงานคำนวณออกไปทำใน `loop()`
เหลือไว้ในคอลแบ็กเฉพาะการคัดลอกข้อมูลดิบ

### ๙. ยังไม่เคยทดสอบบนฮาร์ดแวร์จริงแม้แต่ครั้งเดียว

ระบุไว้ตรงไปตรงมาแล้วใน README ทุกรุ่นและในหัวไฟล์ทุกไฟล์ ซึ่งถูกต้อง
แต่ต้องย้ำว่า **ทุกข้อในเอกสารนี้เป็นการตรวจโค้ด ไม่ใช่การตรวจของจริง**
ยังไม่มีใครรู้ว่าเซนเซอร์อินฟราเรดจับหยดได้จริงหรือไม่ในแสงวอร์ดตอนกลางคืน
หรือระยะสัญญาณครอบคลุมทั้งหอผู้ป่วยหรือเปล่า
