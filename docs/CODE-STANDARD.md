# มาตรฐานคอมเมนต์ของโครงการ

เอกสารนี้กำหนดรูปแบบคอมเมนต์ที่ทุกไฟล์ซอร์สของเฟิร์มแวร์ต้องมี
เพื่อให้เปิดไฟล์ขึ้นมาแล้ว **รู้ทันทีว่าไฟล์นี้คืออะไร เวอร์ชันอะไร และมีอะไรเปลี่ยนมาบ้าง**
โดยไม่ต้องไปไล่อ่าน `git log` หรือ `VERSIONS.md`

รูปแบบที่ใช้คือ **Doxygen** ซึ่งเป็นมาตรฐานที่ใช้กันทั่วไปในงานเฟิร์มแวร์
แท็กทุกตัวในเอกสารนี้เป็นแท็กจริงของ Doxygen ไม่ได้คิดขึ้นเอง
ถ้าวันหนึ่งอยากสร้างเอกสารอัตโนมัติจากโค้ด ก็รัน Doxygen ได้เลยโดยไม่ต้องแก้อะไร

มาตรฐานนี้และตัวตรวจ **ยกมาจากโครงการ MCUPR-CANTEEN** ของผู้พัฒนาคนเดียวกัน
เพื่อให้ทั้งสองโครงการอ่านเหมือนกัน คนที่ย้ายไปมาระหว่างสองโครงการจึงไม่ต้องปรับตัว

## 1. หัวไฟล์ (บังคับทุกไฟล์)

ทุกไฟล์ `.ino` และ `.h` ใน `firmware/` ต้องขึ้นต้นด้วยบล็อกนี้
**หัวไฟล์อยู่บนสุดเสมอ** ถ้ามี `#pragma once` ให้อยู่ถัดลงมา

```c
/**
 * @file      ชื่อไฟล์.h
 * @brief     ไฟล์นี้ทำอะไร หนึ่งบรรทัด
 * @version   4.7.7-OLED
 * @date      2026-09-23
 * @author    นายกิตติพันธ์ รัตนคร <kittiphun.rut@mcu.ac.th>
 *
 * @par Organization
 * วิทยาลัยพยาบาลบรมราชชนนี แพร่ คณะพยาบาลศาสตร์ สถาบันพระบรมราชชนก
 * หอผู้ป่วยอายุรกรรม โรงพยาบาลสูงเม่น จังหวัดแพร่
 *
 * @par Hardware
 * บอร์ดและอุปกรณ์ที่ไฟล์นี้ใช้ (เฉพาะไฟล์ .ino)
 *
 * @par Description
 * คำอธิบายยาวได้ตามต้องการ ว่าไฟล์นี้รับผิดชอบส่วนไหนของระบบ
 *
 * @par Revision History
 * | Version | Date | Change |
 * |---|---|---|
 * | 4.7.7-OLED | 2026-09-23 | สิ่งที่เปลี่ยนในเวอร์ชันนี้ |
 * | 4.7.6-OLED | 2026-09-23 | สิ่งที่เปลี่ยนในเวอร์ชันก่อน |
 *
 * @warning  เรื่องที่ถ้าไม่รู้แล้วจะพัง
 * @note     เรื่องที่ควรรู้แต่ไม่ถึงกับพัง
 */
```

### กติกาของแต่ละแท็ก

| แท็ก | บังคับ | กติกา |
|---|---|---|
| `@file` | ✅ | ต้องตรงกับชื่อไฟล์จริง |
| `@brief` | ✅ | หนึ่งบรรทัด ไม่เกินหนึ่งประโยค |
| `@version` | ✅ | ไฟล์ `.ino` ต้องตรงกับ `APP_VERSION` **เป๊ะ รวมส่วนต่อท้าย** เช่น `4.7.7-OLED` · ไฟล์ `.h` คือ **เวอร์ชันที่ไฟล์นี้ถูกแก้ครั้งล่าสุด** ต้องเป็นแถวบนสุดของตารางตัวเอง และต้องไม่ใหม่กว่า `APP_VERSION` |
| `@date` | ✅ | รูปแบบ `YYYY-MM-DD` เท่านั้น คือวันที่แก้ไขล่าสุด |
| `@author` | ✅ | ชื่อผู้พัฒนาหลัก |
| `@par Revision History` | ✅ | ตารางเรียงจาก**ใหม่ไปเก่า** แถวบนสุดต้องตรงกับ `@version` · ใส่เฉพาะเวอร์ชันที่ไฟล์นี้**ถูกแก้จริง** |
| `@par Hardware` | เฉพาะ `.ino` | บอร์ด จอ และผังขา |
| `@warning` / `@note` | ตามสมควร | ใส่เมื่อมีเรื่องที่คนมารับช่วงต่อต้องรู้ |

> ตรวจอัตโนมัติด้วย `bash tools/header-check/run.sh`
> ถ้าลืมขยับเลขเวอร์ชันหรือลืมเติมแถวใหม่ในตาราง ตัวตรวจจะฟ้อง

### เลขเวอร์ชันของไฟล์ .h ไม่ต้องตามไฟล์หลักเสมอไป

**ตัวอย่างจริงในรีโพนี้** `firmware/Host-OLED/web_dashboard.h` ค้างอยู่ที่ `4.7.6`
ขณะที่สเก็ตช์เป็น `4.7.7-OLED` เพราะรุ่น 4.7.7 แยกแต่โค้ดวาดจอ ไม่ได้แตะหน้าเว็บเลย
**นี่คือสิ่งที่ถูกต้อง** การไล่ขยับเลขทุกไฟล์ให้เท่ากันหมดจะทำให้ตารางโกหกว่า
ไฟล์นั้นถูกแก้ทั้งที่ไม่ได้แก้

### ไฟล์ที่ใช้ร่วมกันหลายสเก็ตช์

`drop_detector.h` อยู่ทั้งใน `firmware/Station/` และ `firmware/Station-C3-OLED/`
และต้องเหมือนกันทุกไบต์ แต่สองสเก็ตช์นั้นใช้เลขเวอร์ชันคนละสาย (`7.8.0` กับ `1.0.0-C3`)
จึงเทียบกับ `APP_VERSION` ไม่ได้ ไฟล์แบบนี้ใช้ **เลขเวอร์ชันของอัลกอริทึมเอง**
และถูกยกเว้นจากการเทียบใน `headercheck.py` (ดูตัวแปร `SHARED` ในไฟล์นั้น)

## 2. ป้ายบอกเวอร์ชันในโค้ด

หัวไฟล์บอกภาพรวม แต่ไม่ได้บอกว่า **บรรทัดไหน** เพิ่มมาตอนไหน
เวลาเพิ่มหรือแก้อะไรที่ไม่ใช่เรื่องเล็ก ให้ปักป้ายไว้เหนือจุดนั้น

```c
// [4.7.6-OLED] เพิ่ม: เกาะเราเตอร์เป็นหลัก ต่อสำเร็จเมื่อใดปิด AP ทิ้ง ภาระ AP หายหมด
void startStaMode() {
```

รูปแบบคือ `// [เลขเวอร์ชัน] คำกริยา: คำอธิบาย` โดยคำกริยาใช้สามคำนี้เท่านั้น

| คำกริยา | ใช้เมื่อ |
|---|---|
| **เพิ่ม** | ของใหม่ที่ไม่เคยมีมาก่อน |
| **แก้** | ของเดิมที่ทำงานผิดแล้วซ่อม |
| **ย้าย** | ของเดิมที่ย้ายที่อยู่ ตรรกะไม่เปลี่ยน |

เลขเวอร์ชันในป้ายต้องมีอยู่จริงในตาราง Revision History ของไฟล์นั้น
ตัวตรวจจะฟ้องถ้าปักป้ายด้วยเลขที่ไม่มีในตาราง

**ไม่ต้องปักป้ายกับ** การแก้คำผิด จัดย่อหน้า เปลี่ยนชื่อตัวแปร
หรือการแก้เล็ก ๆ ที่อ่านโค้ดแล้วเข้าใจได้เอง ป้ายที่เยอะเกินไปจะกลายเป็นขยะ

### ป้ายติดไปข้างหน้า ไม่ย้อนหลังด้วยการเดา

ตอนวางมาตรฐานนี้ ผมปักป้ายเฉพาะจุดที่ **รู้แน่ชัด** ว่าเวอร์ชันไหนเป็นคนเพิ่ม
ไม่ได้ไล่ปักย้อนหลังทั้งรีโพ เพราะการเดาว่าโค้ดก้อนไหนมาจากเวอร์ชันใด
แล้วเขียนลงไปให้ดูครบ คือการใส่ข้อมูลผิดลงในโค้ด ซึ่งแย่กว่าการไม่มีป้าย

## 3. คอมเมนต์ในเนื้อโค้ด

- **เขียนเป็นภาษาไทย** เพราะคนที่มารับช่วงดูแลต่อคือนิสิตและเจ้าหน้าที่ของวิทยาเขต
  ส่วนข้อความที่ผู้ใช้เห็นบนจอเป็นภาษาอังกฤษ และบนหน้าเว็บเป็นภาษาไทย คนละเรื่องกัน

- **อธิบายว่าทำไม ไม่ใช่ทำอะไร** โค้ดบอกอยู่แล้วว่าทำอะไร
  สิ่งที่โค้ดบอกไม่ได้คือเหตุผล เช่น
  *"ห้ามเรียก `esp_wifi_set_channel()` ขณะอยู่โหมด STA เพราะช่องถูกกำหนดโดยเราเตอร์
  ถ้าไปบังคับกลับเป็นช่อง 1 ลิงก์เราเตอร์จะพังทันที"*

- **ห้ามเขียนคอมเมนต์รับประกันสิ่งที่ยังไม่ได้ทดสอบ**
  เฟิร์มแวร์ทั้งหมดในรีโพนี้ยังไม่เคยขึ้นฮาร์ดแวร์จริง ถ้ายังไม่ได้ทดสอบให้เขียนตรง ๆ
  ว่ายังไม่ได้ทดสอบ อย่าเขียนว่า "ปลอดภัย" หรือ "ใช้ได้แน่"

### ห้ามมีภาษาไทยในโค้ดที่วาดลงจอ

ฟอนต์ในตัวของ U8g2 และ Adafruit GFX **มีแต่ ASCII** ไบต์ตั้งแต่ `0x80` ขึ้นไปจะถูกวาด
เป็นสัญลักษณ์มั่ว ภาษาไทยหนึ่งตัวกินสามไบต์ จึงกลายเป็นตัวประหลาดสามตัว
และ **กินที่กว้างกว่าที่โค้ดนับไว้สามเท่า** ข้อความจึงล้นไปทับของข้างเคียง

- สตริงที่ส่งเข้า `drawStr()` / `drawString()` ต้องเป็น ASCII ล้วน
- คอมเมนต์ในไฟล์วาดจอเป็นภาษาไทยได้ตามปกติ เพราะไม่ได้ถูกวาด

## 4. การพิสูจน์ว่าแก้คอมเมนต์แล้วโค้ดไม่เปลี่ยน

การจัดคอมเมนต์ครั้งใหญ่มีความเสี่ยงที่จะเผลอแตะโค้ดไปด้วย รีโพนี้พิสูจน์สองชั้น

1. **เทียบโค้ดที่ลอกคอมเมนต์ออกแล้ว** ระหว่างของเดิมกับของใหม่ ต้องได้ค่าแฮชตรงกัน
2. **เรนเดอร์ภาพหน้าจอทุกหน้าแล้วเทียบทีละพิกเซล** ตามวิธีในหัวข้อ
   "การพิสูจน์ว่าแก้แล้วพฤติกรรมไม่เปลี่ยน" ของ `CLAUDE.md`

ตอนวางมาตรฐานนี้ ผ่านทั้งสองชั้น — โค้ดเหมือนเดิม 18/18 ไฟล์ และภาพเหมือนเดิม 119/119 ภาพ

## 5. ตรวจก่อน commit ทุกครั้ง

```bash
bash tools/header-check/run.sh          # หัวไฟล์ Doxygen และป้ายเวอร์ชัน
bash tools/split-check/run.sh           # ปัญหาจากการแยกโค้ดไปไว้ในไฟล์ .h
python3 tools/check-ino-types.py        # ลำดับการประกาศชนิดข้อมูลของ Arduino
bash tools/protocol-test/run.sh         # โครงสร้างแพ็กเก็ตตรงกันทุกรุ่น
```

ชุดเต็มอยู่ในหัวข้อ "ชุดตรวจก่อน commit" ของ `CLAUDE.md`

ทุกตัวไม่ได้แทนการคอมไพล์ เป็นแค่ตัวกันความผิดพลาดที่เคยเกิดขึ้นจริงมาแล้ว
**การคอมไพล์และทดสอบบนเครื่องจริงยังจำเป็นเสมอ**
