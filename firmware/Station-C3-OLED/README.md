# Bed Station Node v1.0.0-C3 — บอร์ดเล็ก ESP32-C3 + จอ OLED 0.42"

เครื่องประจำเตียงอีกแบบหนึ่ง ใช้บอร์ด **ESP32-C3 Super Mini** กับจอ **SSD1306 ขนาด 0.42 นิ้ว
ความละเอียด 72x40** ต่างจากสายหลักที่ใช้ ESP32-S3 กับจอ TFT สี

ปรับปรุงจากไฟล์ `ESP32-C3-Station-V_4_4_2.ino` ที่มีอยู่เดิม ให้เข้ากับระบบรุ่นปัจจุบัน

## ทำไมของเดิมใช้กับระบบรุ่นนี้ไม่ได้

**คุยกับ Host รุ่นปัจจุบันไม่ได้เลย** เพราะโครงสร้างแพ็กเก็ตคนละแบบ

| | ของเดิม v4.4.2 | Protocol v3 (รุ่นนี้) |
|---|---|---|
| `struct_message` | 14 ไบต์ | **23 ไบต์** |
| ข้อมูลที่ส่ง | ไม่มี `flowRateHr`, `msSinceLastDrop`, `flags` | ครบ |
| แพ็กเก็ตจาก Host | `struct_time_sync` 5 ไบต์ (มีแค่เวลา) | **`struct_host_sync` 20 ไบต์** |
| รับจาก Host ได้ | เวลาอย่างเดียว | เวลา, เป้าหมาย, ปริมาตรตามแผน, รหัสเตือน, drop factor, สั่งเริ่มถุงใหม่ |

Host จะเห็นเครื่องนี้เป็น OFFLINE ตลอด เพราะความยาวแพ็กเก็ตไม่ตรง จึงถูกทิ้งตั้งแต่ต้น

## สิ่งที่แก้ เรียงตามความสำคัญ

### 1. โครงสร้างแพ็กเก็ตเป็น Protocol v3

มี `static_assert` ตรึงขนาดไว้ที่ 23 และ 20 ไบต์ คอมไพล์ไม่ผ่านทันทีถ้ามีใครแก้จนเพี้ยน
และ `bash tools/protocol-test/run.sh` ตรวจซ้ำอีกชั้นว่าตรงกับทุกเฟิร์มแวร์ในโครงการ

ผลพลอยได้คือ **drop factor มาจาก Host** ตามแผนการรักษาจริง ของเดิมตรึงไว้ที่ 20 ในโค้ด

### 2. การหาช่องสัญญาณ — ข้อนี้ทำให้ของเดิมใช้ไม่ได้ตั้งแต่ Host v4.7.6

ของเดิมสแกนหาชื่อ Wi-Fi `ESP32_Liquid_Monitor` **ครั้งเดียวตอนบูต** แล้วตรึงช่องไว้

```cpp
currentChannel = findHostChannel();          // ของเดิม เรียกครั้งเดียว
esp_wifi_set_channel(currentChannel, ...);
```

ตั้งแต่ Host v4.7.6 เป็นต้นไป Host เกาะเราเตอร์ของโรงพยาบาลเป็นหลักและ **ปิด Access Point ทิ้ง**
ชื่อ Wi-Fi นั้นจึงไม่มีให้สแกนอีกแล้ว และช่องสัญญาณเป็นของเราเตอร์ ไม่ใช่ช่อง 1

รุ่นนี้ใช้ `manageChannelHunting()` แบบเดียวกับสายหลัก — ไล่ช่อง 1 ถึง 13 ช่องละ 2.5 วินาที
เมื่อไม่ได้ยิน Host แล้วจำช่องที่เจอลง NVS อย่างช้าที่สุด **32.5 วินาที** ก็กลับมาออนไลน์

### 3. เสียงออดไม่บล็อกลูปอีกต่อไป

ของเดิมใช้ `delay()` ระหว่างส่งเสียง ลูปทั้งเครื่องหยุดเดิน ตรวจจับหยดไม่ทัน
เสียงยืนยันตอนคาลิเบรตของเดิมยาวถึง 800 ms หมายถึงหยดที่ตกในช่วงนั้นหายไปเลย

รุ่นนี้เป็นคิวจังหวะ สั่ง `beepPattern(3, 90, 70)` แล้วกลับมาทำงานต่อทันที
มี `serviceBeep()` ในลูปคอยเปิดปิดออดตามเวลา

### 4. สูตรอัตราการไหล

ของเดิมนับหยดในหน้าต่าง 2.5 วินาทีแล้วคูณขึ้นเป็นต่อนาที

```cpp
currentGttMin = (dropsInLastWindow / intervalSec) * 60.0;   // ของเดิม
```

ที่อัตรา 20 หยดต่อนาที หน้าต่าง 2.5 วินาทีมีหยดเฉลี่ยไม่ถึงหนึ่งหยด ตัวเลขบนจอจึงกระโดด
ระหว่าง 0 กับ 24 กับ 48 ตลอดเวลา อ่านไม่ได้

รุ่นนี้ใช้หน้าต่างสะสม 8 หยดแบบเดียวกับสายหลัก วัดช่วงเวลาที่ครอบหลายหยดแล้วหารครั้งเดียว
(เหตุผลเชิงสถิติอยู่ในหัวข้อ "หน้าต่างคำนวณอัตราไหล" ในไฟล์ `.ino`)

### 5. ตัวตรวจจับหยดตัวเดียวกับสายหลัก

ใช้ `drop_detector.h` ซึ่งเป็นไฟล์เดียวกันทุกไบต์กับ `firmware/Station/`
เรียนรู้รูปคลื่นเองไม่ต้องคาลิเบรตด้วยมือ และตัดการแกว่งของถุงตอนคนไข้เดินออกได้

ของเดิมใช้เกณฑ์คงที่กับฮิสเทอรีซิส ซึ่งถุงแกว่งก็นับเป็นหยด และต้องคาลิเบรตสองขั้นทุกครั้ง

### 6. ตั้งเลขเตียงที่หน้าเครื่อง

ของเดิมต้องแก้ `#define STATION_ID` แล้วคอมไพล์ใหม่ทีละเตียง ใช้จริงในหอผู้ป่วยไม่ไหว
รุ่นนี้กดปุ่มค้าง 4 วินาทีเข้าหน้าตั้งเลข กดสั้นเพิ่มเลข กดค้างบันทึกลง NVS

## หน้าจอ 72x40 ออกแบบใหม่ทั้งหมด

จอนี้เล็กมาก วางตัวอักษร 4x6 ได้ 18 ตัวต่อบรรทัด และราว 5 บรรทัดเท่านั้น
จึงใช้หลักสามข้อ (รายละเอียดอยู่ในหัวไฟล์ `StationScreen.h`)

1. **หนึ่งหน้าจอ หนึ่งคำตอบ** ตัวเลขที่ตอบคำถามนั้นใช้ฟอนต์สูง 16 พิกเซล = 40% ของความสูงจอ
2. **หัวจอไม่เคยหาย** เลขเตียง สถานะการเชื่อมต่อ และนาฬิกา อยู่ครบทุกหน้า
3. **เหตุที่ต้องรีบไปดูคนไข้ กินทั้งจอ** หน้าเตือนกลับสีทั้งหน้าและกะพริบ

### หน้าที่มี

| หน้า | ตอบคำถาม | แสดง |
|---|---|---|
| RATE | ตอนนี้ไหลเท่าไร ตรงตามแผนไหม | mL/h ตัวใหญ่ · เป้าหมาย · กระเปาะหยด · แถบความคืบหน้า |
| GTT | นับหยดเทียบกับที่ตั้งไว้ตรงไหม | gtt/min ตัวใหญ่ · เป้าหมายเป็นหยดต่อนาที |
| VOLUME | ให้ไปแล้วเท่าไร นับได้กี่หยด | ปริมาตร/แผน · จำนวนหยดสะสม · สถานะเซนเซอร์ |
| STATUS | เครื่องปกติดีไหม | เลขเตียง · ช่อง · การเชื่อมต่อ · เซนเซอร์ · แบตเตอรี่ |

### กระเปาะหยด — "แสดงการนับ" ให้เห็นด้วยตา

หยดบนจอ **ล็อกกับเวลาจริงของหยดล่าสุด** ไม่ใช่อนิเมชันลอย ๆ
หยดที่เห็นบนจอจึงตกพร้อมกับหยดจริงในกระเปาะ พยาบาลใช้เทียบด้วยตาได้ว่าเครื่องนับตรงหรือไม่
ถ้าหยดหยุดเกินสามเท่าของจังหวะปกติ กระเปาะจะหยุดวาดหยด ไม่หลอกตา

### สถานะเซนเซอร์มาก่อนเป้าหมายเสมอ

ถ้าตัวตรวจจับยังเรียนรู้ไม่เสร็จ ช่องที่ปกติแสดงเป้าหมายจะขึ้นคำว่า `LEARN` แทน
เพราะระหว่างนั้นตัวเลขบนจอยังเชื่อไม่ได้ พยาบาลต้องรู้ข้อนี้ก่อน

### ปุ่มเดียว ทำได้ครบ

| การกด | ผล |
|---|---|
| กดสั้น 1 ครั้ง | เปลี่ยนหน้า (ที่หน้าเตือนใกล้หมด = กดรับทราบ ส่งกลับ Host) |
| กดสั้น 2 ครั้ง | เริ่ม / หยุดชั่วคราว |
| กดสั้น 3 ครั้ง | เข้าตัวช่วยคาลิเบรตสี่ขั้นตอน |
| กดค้าง 1.5 วินาที | กลับหน้าแรก (ในตัวช่วยคาลิเบรต = ออกโดยไม่บันทึก) |
| กดค้าง 4 วินาที | เข้าหน้าตั้งเลขเตียง (ในหน้านั้น กดสั้น = เพิ่มเลข กดค้าง = บันทึก) |

### ตัวช่วยคาลิเบรตสี่ขั้นตอน

ตัวตรวจจับเรียนรู้รูปคลื่นหยดเองได้อยู่แล้ว แต่เดิมมีปัญหาสองข้อ
**ไม่มีใครรู้ว่าวางเซนเซอร์ถูกตำแหน่งหรือยัง** จนกว่าจะยืนรอดูว่ามันนับหรือเปล่า
และ **สิ่งที่เรียนรู้ไว้หายทุกครั้งที่ปิดเครื่อง** เปิดมาต้องเรียนใหม่ทุกที
ทั้งสองข้อคือความล้มเหลวแบบเงียบ เพราะจอขึ้นว่าทำงานปกติทั้งที่ยังไม่นับอะไรเลย

แบ่งเป็นสี่ขั้นเพราะแต่ละขั้นตอบคำถามคนละข้อ และบอกได้ว่าต้องไปแก้ตรงไหน

| ขั้น | ต้องทำอะไรกับสาย | ผ่านเมื่อ | ตัวเลขบนจอ |
|---|---|---|---|
| 1 `BASELINE` | ปิดโรลเลอร์แคลมป์ | นิ่งต่อเนื่อง 3 วินาที ไม่มีหยดหลุด | `n` = สัญญาณรบกวน · `RAW HI`/`RAW LO` = ค่าดิบผิดปกติ |
| 2 `DIRECTION` | เปิดแคลมป์ให้หยด | เห็น 3 หยด และสรุปทิศได้ | `DROP LO` = หยดทำให้ค่าลดลง |
| 3 `LEARN` | ปล่อยให้หยดต่อไป | ครบ 10 หยด และ SNR ≥ 6 เท่า | นับหยด `n/10` |
| 4 `VERIFY` | ปล่อยให้หยดต่อไป | ครบ 10 หยด ความสม่ำเสมอ ≥ 60% | นับหยด `n/10` |

ผ่านครบสี่ขั้นแล้วกดหนึ่งครั้งเพื่อบันทึกลง NVS เปิดเครื่องครั้งหน้าพร้อมนับทันที
ขั้นไหนไม่ผ่านในเวลาที่กำหนด จอจะกลับสีทั้งแถบและบอกสาเหตุเป็นสิ่งที่ลงมือแก้ได้
เช่น `check wiring` `too bright` `hold still` `too few drops` `weak signal`
แก้แล้วกดหนึ่งครั้งเพื่อลองขั้นเดิมใหม่ ไม่ต้องเริ่มจากขั้นแรก

**เวลารอของแต่ละขั้นไม่เท่ากัน** ขั้นที่ 1 ให้ 20 วินาที ขั้นที่ต้องรอหยดให้ 180 วินาที
เพราะจำนวนหยดขึ้นกับอัตราการไหลของผู้ป่วย ที่ 20 mL/h กับ drop factor 20
คือ 9 วินาทีต่อหยด สิบหยดใช้เวลาราว 90 วินาที

**ขั้นที่ 2 วัดทิศสัญญาณเอง ไม่ได้รออ่านผลจากตัวตรวจจับ** เพราะกลไกหาทิศในตัว
`drop_detector.h` เป็นการลองผิดลองถูก ให้เวลาทิศละ 10 วินาที ครบแล้วยังจับจังหวะ
ไม่ได้ก็สลับทิศ ที่อัตราไหลปกติกว่าจะจับจังหวะได้สม่ำเสมอต้องใช้ราว 5 หยด ซึ่งเกิน
10 วินาที มันจึงสลับไปทิศที่ผิดแล้วล็อกทิศนั้นไว้ ตัวเลขยังนับได้เพราะไปเกาะไหล่ของ
พัลส์แทนตัวพัลส์ แต่ความสูงที่วัดได้เหลือครึ่งเดียว SNR จึงตกลงครึ่งหนึ่ง
ขั้นนี้จึงเทียบค่าดิบกับค่าเฉลี่ยของตัวเองแล้วดูว่าเบี่ยงไปทางไหนมากกว่า
ได้คำตอบภายในสามหยดและไม่ขึ้นกับว่าตัวตรวจจับจะจับจังหวะได้เมื่อไร

## การต่อสาย

คงผังขาเดิมของบอร์ด v4.4.2 ไว้ทุกขา ไม่ต้องแก้สายที่ประกอบไว้แล้ว

| อุปกรณ์ | ขา |
|---|---|
| TCRT5000 ขา AO | GPIO 4 |
| ตัวแบ่งแรงดันแบตเตอรี่ | GPIO 0 |
| ออดแบบมีวงจรกำเนิดเสียงในตัว | GPIO 3 (สั่งงานด้วยลอจิกสูง) |
| ปุ่มกด | GPIO 7 (ต่อลงกราวด์) |
| จอ OLED I2C | SCL GPIO 6 · SDA GPIO 5 |

## ดูหน้าจอโดยไม่ต้องมีบอร์ด

```bash
bash tools/c3-preview/run.sh          # ภาพออกที่ docs/screens-c3/
```

เครื่องมือนี้ **ป้อนสัญญาณหยดสังเคราะห์เข้าตัวตรวจจับตัวจริง** ไม่ใช่ตั้งค่าสถานะลัด
ภาพที่ได้จึงสะท้อนพฤติกรรมจริงของอัลกอริทึม รวมถึงคำว่า `LEARN` ที่ขึ้นก่อนแล้วเปลี่ยนเป็น
เป้าหมายเมื่อเรียนรู้เสร็จ

## ข้อจำกัด

เฟิร์มแวร์นี้ **ยังไม่ได้ทดสอบบนฮาร์ดแวร์จริง** ตรวจด้วยเครื่องมือจำลองบน PC เท่านั้น
สิ่งที่ควรดูเป็นอันดับแรกตอนมีบอร์ดจริง

1. **แอมพลิจูดของสัญญาณ TCRT5000 บนบอร์ด C3** — ADC ของ C3 เป็นคนละตัวกับ S3
   ค่า `DetectorConfig` ที่ยกมาจากสายหลักอาจต้องปรับ
2. **เวลาที่ใช้ไล่หาช่องจริง** ค่า 32.5 วินาทีเป็นค่าคำนวณจากโค้ด ยังไม่ได้จับเวลาจริง
3. **ความคมของจอ 0.42 นิ้ว** ฟอนต์สูง 16 พิกเซลบนจอกว้าง 1 เซนติเมตรกว่า ๆ
   ต้องดูของจริงว่าพยาบาลอ่านจากปลายเตียงได้ในระยะเท่าใด
